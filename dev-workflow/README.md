## 用途

`dev-workflow` 用于约束模块化软件开发的准备和执行过程，主要解决以下问题：

- 开发内容局部正确，却偏离项目主线。
- 模型从旧代码、注释或示例中擅自推断业务需求。
- 需求、技术方案、任务和验收之间逐渐脱节。
- 小改动流程过重，大改动调查不足。
- 方案确认后仍不断询问普通实现细节。
- 开发暂停或跨会话后无法可靠恢复。
- 只完成静态检查，却被误报为已经完整验证。

它不能证明软件绝对正确，也不能验证现实中的组织身份。它通过需求来源、证据边界、风险门禁、开发合同和验证记录降低偏离与遗漏风险。

## 适用范围

适合：

- 新增或修改模块、组件、服务和接口。
- 修改 Schema、配置、状态流程、权限和数据映射。
- 重构、迁移、集成及开发文档变更。
- 只读的需求、契约、数据流和影响分析。
- 需要跨会话持续推进的开发工作。

通常不用于：

- 翻译、改写和精确格式调整。
- 查询时间等简单事实。
- 不涉及软件结构、行为或开发产物的任务。

## 核心原则

### 需求与实现证据分轨

需求只能来自：

- 当前使用者的明确决定。
- 有效的客户或产品需求。
- 已批准的验收标准。
- 当前项目中生效的规则和规格。

代码、配置、Schema、运行行为和测试只能说明系统当前如何工作、存在哪些约束以及如何实现，不能用来补充或确认需求。

当需求没有说明某项行为，而旧代码存在该行为时，skill 会把需求标记为未知，不会默认保留或删除。

### 当前使用者是默认决策者

Skill 默认当前使用者有权为本次任务作出需求决定，不要求使用者证明现实身份。如果项目已有明确审批规则，则继续遵守项目规则。

### 只禁止未披露的重大假设

会改变以下内容的未知项属于重大未知项：

- 项目方向、需求范围或业务规则
- 用户可见行为或验收结果
- API、Schema、数据含义或兼容性
- 权限、安全、隐私或租户边界
- 状态、持久化或外部副作用
- 模块职责、公共接口或依赖方向
- 错误、幂等、回滚或数据损失风险
- 必需验证和完成判定

局部命名、等价内部实现等不影响契约和验收的选择由模型自行处理。

## 总体流程

```text
确认有效需求来源
        ↓
Gate 0：项目方向对齐
        ↓
确定当前可交付增量
        ↓
评估 LOW / MEDIUM / HIGH 风险
        ↓
迭代调查需求、技术和数据契约
        ↓
闭合所有受影响路径
        ↓
形成需求—任务—验收—验证开发合同
        ↓
获得所需实施确认
        ↓
READY TO DEVELOP
        ↓
按照计划连续执行和逐项验证
        ↓
全部必需验证取得证据
        ↓
VERIFIED
```

调查阶段不是严格瀑布流程。模型可以在需求、技术和契约之间往返查证，但在重大未知项解决前不能形成依赖该未知项的方案或修改。

## 当前可交付增量

Skill 不要求整个项目所有未来需求全部明确。每次开发只需同时满足：

- 项目方向和当前里程碑明确。
- 本次可交付增量的需求、契约和验收完整。
- 未来需求被明确排除在当前范围之外。
- 当前方案没有替未知的未来需求作出难以撤销的决定。

执行过程中新增需求如果不影响当前合同，会进入后续增量；如果改变当前需求、契约或验收，则触发暂停和重新评估。

## 需求基线与变更

当完整旧需求仍然有效，而新的大需求文档只描述部分变化时，采用：

```text
有效需求 = 当前完整基线 + 已确认的增量变更
```

变更关系包括：

- `ADD`：明确新增。
- `MODIFY`：明确修改对应基线需求。
- `DELETE`：明确删除对应基线需求。
- `INHERIT`：新文档未提及，继续继承。
- `AMBIGUOUS`：影响不明确，需要使用者裁决。

新文档不会因为时间较新而自动废除相关旧需求。稳定后可以把基线和补丁归并为新的完整基线。

## 风险等级

### LOW

只有同时满足下列条件才能判为低风险：

- 需求明确且只有一种合理解释。
- 改动位于一个已知责任边界。
- 不改变公共契约、数据含义、权限、状态、持久化或外部副作用。
- 不影响生产环境。
- 容易撤销。
- 验证方式明确。
- 重大未知项为零。

低风险任务使用紧凑流程，明确的修改请求本身即可作为实施授权。

### MEDIUM

命中任一情况至少为中风险：

- 改变用户可见行为。
- 跨模块或影响多个消费者。
- 修改内部接口、配置、状态或持久化行为。
- 引入依赖或扩展点。
- 存在兼容性要求。
- 需要人工验收。
- 包含多个独立实施任务。

中风险任务会形成完整开发合同、维护过程账本，并在执行前统一确认一次。

### HIGH

命中任一情况即为高风险：

- 身份、权限、安全、隐私、密钥或租户。
- 数据迁移、删除、覆盖或不可逆转换。
- 资金、计费、合规或审计。
- 生产操作或外部系统副作用。
- 破坏公共 API、Schema、协议或兼容性。
- 多系统一致性、并发、幂等或回滚风险。
- 可能造成重大数据损坏或服务中断。

高风险任务还需要持久账本、隔离或回滚方案，以及对应操作的独立授权。

## 开发合同

中高风险任务使用轻量标识建立追踪：

```text
REQ-01：需求
TASK-01：实施任务
AC-01：验收标准
VAL-01：验证方式和证据
```

必须保证：

- 每个任务都对应需求。
- 每个需求都对应验收标准。
- 每个必需验收标准都对应验证方式。
- 需求变更会重新评估受影响的任务和验证。

开发合同还会说明范围、非目标、受影响产物、依赖顺序、副作用、风险、回退边界和授权要求。

## 进入开发后的行为

开发合同确认并进入 `READY TO DEVELOP` 后，模型会按照任务依赖顺序连续执行，不再逐项等待确认。

模型可以自主处理不改变需求、契约、验收或风险边界的实现细节。遇到以下情况会暂停：

- 使用者明确要求暂停。
- 新事实推翻了原需求、技术或契约结论。
- 继续执行必须修改已确认方案。
- 出现新的重大未知项。
- 需要未授权的构建、迁移、部署或外部副作用。
- 环境变化或验证失败超出原修复边界。
- Token、时间或费用预算达到限制。

原方案范围内的普通实现缺陷由模型自行修复并重新验证。

## 验证与完成状态

验证层级包括：

- 静态验证
- 自动化运行验证
- 集成验证
- 数据库验证
- 端到端验证
- 人工验收

每一层会根据任务标记为 `REQUIRED` 或 `N/A`。人工验收只在用户交互、视觉行为、业务流程、主观质量或其他无法自动验证的行为中设为必需。

状态由证据推导：

- `VERIFICATION_PENDING`：实现已存在，但必需验证证据不完整。
- `VERIFICATION_FAILED`：至少一项必需验证失败。
- `VERIFIED`：全部必需验收标准都有通过证据。

静态检查不会被描述成运行验证，Gate 也不使用百分比置信度。

## 账本、暂停与恢复

中高风险任务以及任何跨会话任务都会维护开发过程账本。任何任务一旦暂停，也会被视为跨会话任务。

账本会明确标识：

```yaml
artifact_type: dev-workflow-process-ledger
authority: process-record-only
is_requirement_source: false
```

账本只记录开发过程，不是客户需求或产品规则来源。

建议使用“项目级轻量索引 + 每个开发增量独立账本”：

```text
项目索引
  ├─ 增量 A 账本
  ├─ 增量 B 账本
  └─ 增量 C 账本
```

每个增量账本只允许一个执行流程更新。每次重大决策、Gate 变化、任务结果、验证结果、外部副作用、暂停或恢复后，都必须先同步账本再继续。同步失败时暂停。

暂停检查点会记录：

- 暂停原因
- 最后完成和正在执行的任务
- 已修改产物
- 已执行的外部副作用
- 已完成和待完成验证
- 当前 Gate 和失效 Gate
- 恢复前提
- 下一安全动作

恢复时不会盲目续跑。模型会先核对实际文件、配置、运行状态和外部状态，更新可能过期的证据，重新评估受影响 Gate，并避免重复执行外部副作用。

## 常用调用方式

明确调用：

```text
$dev-workflow 为订单模块增加取消操作。先明确状态、权限、幂等、错误和验收，再按确认后的方案开发。
```

规划但不实施：

```text
$dev-workflow 为新的文件导入格式准备开发合同，不要修改代码。
```

只读分析：

```text
$dev-workflow 分析提交后页面关闭的原因，并区分现有实现和产品要求。
```

暂停：

```text
暂停当前开发，外部接口发生变化。记录检查点，等我补充新需求后再恢复。
```

恢复：

```text
恢复上次暂停的增量。先核对账本、当前文件和外部接口，再重新评估受影响的 Gate。
```

## Skill 文件结构

```text
dev-workflow/
├── SKILL.md
├── README.md
└── references/
    ├── gates.md
    ├── ledger.md
    ├── outputs.md
    └── examples.md
```

- `SKILL.md`：模型执行的核心流程。
- `references/gates.md`：证据、重大性、风险和 Gate 规则。
- `references/ledger.md`：账本、同步、暂停和恢复规则。
- `references/outputs.md`：开发合同、报告和验证模板。
- `references/examples.md`：仅在分类或流程不明确时参考的示例。
- `README.md`：本中文使用说明，不参与模型运行。
